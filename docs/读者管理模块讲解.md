## 一、任务概述

在 5 人并行开发方案中，B 负责**读者管理**这一垂直切片：从数据库访问（DAO 实现）到界面（管理面板 + 对话框）完整交付一个功能板块。读者是借阅业务的前置数据——D 的借书流程第一步就是"选读者"（`readerDao.getByCardNo(cardNo)`），因此本模块的核心质量要求是：

1. **数据准确**：reader 表的增删改查全部走 `PreparedStatement`，reader 表 SQL 只出现在 `ReaderDaoImpl` 中（契约：每张表唯一主拥有者）；
2. **借书证号唯一**：办证防重复、借书时按证号精确定位读者；
3. **不阻塞他人**：只依赖第 1 周冻结的契约接口（`ReaderDao`、`BaseTableModel`、`JDBCConnection`），不依赖 A/C/D/E 的实现细节。

## 三、核心代码讲解

### 1. ReaderDaoImpl —— 数据访问层

**（1）泛型契约的实现**

```java
public class ReaderDaoImpl implements ReaderDao { ... }
```

`ReaderDao extends IBaseDao<Reader>`，编译器保证 `getList()` 返回的一定是 `List<Reader>`，界面层取出来直接用，**无需强制类型转换**——这是教材原始 `List` 写法做不到的（泛型知识点落点）。

**（2）统一的"行转对象"方法**

```java
private Reader toReader(ResultSet rs) throws Exception {
    Reader r = new Reader();
    r.setId(rs.getInt("id"));
    ...
    return r;
}
```

5 个查询方法（`getList`/`getById`/`getByCardNo`…）共用这一个映射方法，避免重复代码；字段名与契约实体定义严格一致。

**（3）PreparedStatement 防注入（课程考核点）**

所有 SQL 的动态值一律用 `?` 占位、`setXxx` 传参，**绝不拼接字符串**：

```java
String sql = "SELECT id, name, sex, tel, cardNo FROM reader WHERE cardNo = ?";
ps = conn.prepareStatement(sql);
ps.setString(1, cardNo);
```

即使有人把借书证号输入成 `' OR '1'='1` 也只会被当作普通字符串查询，SQL 注入无效。

**（4）批量化接口**

`saveList` / `deleteList` 用 `addBatch()` + `executeBatch()` 实现**批量**新增/删除，对应契约中"批量新增（list 中 id=0 的记录）"的语义；单条操作传 `Collections.singletonList(x)` 即可，同一套代码两种用法（集合知识点落点）。

**（5）资源关闭**

每个方法都在 `finally` 中调用 `JDBCConnection.close(conn, ps, rs)` 依次判空关闭——这是教材的标准写法，保证异常发生时连接也不泄漏。

### 2. ReaderAddDialog —— 新增/编辑对话框

**（1）一窗两用（新增 + 编辑）**

```java
public ReaderAddDialog(Frame owner)              { this(owner, null); }  // 新增
public ReaderAddDialog(Frame owner, Reader r)    { ... }                 // 编辑（表单回显）
```

编辑模式传入被编辑对象：回显数据、保留 `id`，保存时走 `update`（整条记录覆盖写），符合契约"按主键更新整条记录"的口径。

**（2）借书证校验（B 的核心业务规则）**

```java
private String validate(String name, String tel, String cardNo) {
    if (name.isEmpty())      return "姓名不能为空";
    if (cardNo.isEmpty())    return "借书证号不能为空";
    if (!tel.isEmpty() && !tel.matches("\\d{11}")) return "电话必须为 11 位数字";
    Reader exist = readerDao.getByCardNo(cardNo);          // 查库防重复
    if (exist != null) {
        boolean unchanged = reader != null && exist.getId() == reader.getId();
        if (!unchanged)     return "借书证号已存在：" + cardNo;
    }
    return null;  // 校验通过
}
```

校验分两档：
- **格式校验**（不查库）：非空检查、电话 11 位数字正则 `\\d{11}`；
- **唯一性校验**（查库）：调 `getByCardNo` 查重。注意**编辑时排除自己**——把某读者的证号原样保存回去不应误报"已存在"，判断依据是查到的记录 id 与被编辑对象 id 相同。

**（3）与父面板的交互约定**

对话框不直接刷新表格（它不知道表格存在），而是暴露 `isSaved()` 状态，由 `ReaderManagePane` 在对话框关闭后决定是否刷新——**边界类之间解耦**。

### 3. ReaderManagePane —— 管理面板

**（1）表格：契约工具 BaseTableModel（反射，E 提供）**

```java
private static final String[] COLUMNS = {"编号", "姓名", "性别", "电话", "借书证号"};
private static final String[] PROPS   = {"id",   "name",  "sex",   "tel",  "cardNo"};

tableModel = new BaseTableModel<Reader>(null, COLUMNS, PROPS);
table = new JTable(tableModel);
```

列名数组与**实体属性路径**数组一一对应，`BaseTableModel` 内部用反射拼 getter 取值。B 不为 Reader 手写任何 TableModel——如果契约改了列顺序，只改这两个数组即可。

**（2）数据流：每次操作后整表重查**

```
按钮点击 → readerDao.xxx() 增删改 → refreshTable() 重新 getList() → setList() 触发 fireTableDataChanged
```

放弃"本地缓存增量维护"，每次都从数据库重查。读者数据量小，这样写**最简单也最不容易出现界面与库不一致**，是课程项目的合理取舍（答辩可以主动讲这个 trade-off）。

**（3）删除的防呆设计**

未选中行时提示"请先选择"；选中后弹 `showConfirmDialog` 二次确认；删除后刷新。双击行快捷进入编辑（`MouseAdapter` 监听 `getClickCount() == 2`）。

**（4）按证号查询（服务借书场景）**

输入证号点"按证号查询"→ `getByCardNo` 精确查询：查到则表格只显示这一位读者（借书时快速定位），查不到弹警告提示。这与 D 的 `BorrowPane` 中"输入证号选读者"用的是**同一个契约方法**，行为口径一致。
